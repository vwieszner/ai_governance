## 1. Finding (triaged) — missing `Authorization` header returned 422, not 401

**Probes:** P1 (no-auth submit) on all 4 backends; P6 (unauth task read) on A2A :8000/:8002.
Red-team's auto-classifier flagged 6 results as VULNERABLE because the observed status (422) did
not match the expected 401/403.

**Triage verdict: REAL but LOW severity — a status-code/hygiene bug, NOT an authz bypass.**
The request was still rejected with no data returned; only the *status code* was wrong. An
unauthenticated caller got `422 Unprocessable Entity` (FastAPI's "field required" for a missing
header) instead of the semantically correct `401 Unauthorized`. Evidence it was never a bypass:
malformed/forged tokens already returned 401 in the same run (P2 alg:none, P3 tampered sig, P4
garbage bearer all DEFENDED), and every protected path still refused to serve.

**Root cause (verified, not guessed):** the auth dependency declared the header as required —
`authorization: str = Header(...)`. FastAPI validates required headers *before* the handler body,
so a wholly-absent header produced a 422 validation error and the body's explicit 401 path was
never reached. (The body already returned 401 for a present-but-malformed header.)

**Fix (root, both solutions — fail closed with 401 + RFC 6750 challenge):**
- `federated-rag/api/main.py` → `get_token_claims`: param changed to
  `authorization: str | None = Header(default=None)`; added an explicit
  `if not authorization: raise HTTPException(401, "Missing Authorization header",
  headers={"WWW-Authenticate": "Bearer"})` before parsing.
- `agt-federated-rag/api/main.py` → `POST /query` param made `str | None = Header(default=None)`
  and `_get_bearer_token` guards `if not authorization: raise 401 (+ WWW-Authenticate: Bearer)`
  before `.partition()` (which would otherwise `AttributeError` on `None` → 500).

Both files `py_compile`-clean; all 4 backends restarted via `scripts/clusters.ps1 restart all`.

**Re-test (DEFENDED):** P1 now `HTTP 401 {"detail":"Missing Authorization header"}` on all four
backends; P6 now `HTTP 401` on A2A :8000/:8002. Full re-run: **43 DEFENDED / 0 VULNERABLE / 4
EXPECTED / 0 BLOCKED** (see `RED_FINDINGS.md`, regenerated by the clean re-run).

## 2. EXPECTED results — controls working as designed (NOT vulns)

**P7 ReBAC "pending ≠ read"** on all 4 backends. alice holds only `pending_approval` (not
`viewer`) on the salary chunk. Every backend withheld the data:
- A2A: returned the in-progress/approval status, never the salary figures.
- AGT cluster-a: `"Your request is pending approval…"`.
- AGT cluster-b: routed remote and returned `"…requires approval from the remote data owner."`.

No salary band, compensation figure, or numeric leaked in any case. This is the core
authorization invariant of the system holding: `pending_approval` does not grant reads.

## 4. Reproduce

```powershell
# all four backends must be up:  .\scripts\clusters.ps1 status
.venv\Scripts\python.exe redteam\run_probes.py    # writes redteam/RED_FINDINGS.md
```

`redteam/probe_lib.py` holds the shared helpers (token mint, `alg:none` / tamper forgery, SSE
collection); `redteam/run_probes.py` is the runner. The probes never modify backend source — they
only send HTTP and classify the response.
